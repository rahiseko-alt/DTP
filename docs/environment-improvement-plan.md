# 環境構築改善計画

## ゴールと設計

CodexとClaude Codeが最新mainの各フォルダにあるコード・実データから状態を把握し、両担当の引継ぎノートと突き合わせて編集へ進める状態を構築する。

**状態把握はコードのみ、引継ぎはnoteのみ。** ノートを状態の正本にせず、別の手動現況索引を作らない。旧案のcurrent.yamlは撤去。学校情報・構成・素材の値は適切な既存フォルダへ保存する。

## 原因と対策

| 原因 | 対策 |
| --- | --- |
| 古いノート/READMEの文から現在状態を推測 | フォルダのコード・データ・追跡ファイルを直接取得して読む |
| 情報がノートにしかないのに反映済みと誤認 | 引継ぎとコードを突合し未反映として明記 |
| 古い作業checkoutを最新mainと混同 | fetchした固定main SHAから取得しcheckoutは保持 |
| 通信失敗後の古いcacheを最新と誤認 | 非zero失敗、旧状態cache無効化、offline未検証表示 |
| 状態台帳が古くなる | 手動状態台帳を撤去し正本コードから都度取得 |

## 構築と受入条件

1. 共通Python/Git CLIで最新mainを取得し固定SHAと時刻を表示する。
2. 状態出力はcompany-data・books・references・sharedの実コード/データのみ。追跡パスの構成、メタデータ全文、必要なコード本文を取得できる。
3. 引継ぎは両担当ノートを別ファイルに全文取得。同じSHAの状態と突き合わせる。
4. 両入口を揃え、開始/回答/編集/マージ提案前に取得して読む。
5. 情報・素材・構成の変更は該当フォルダへ、理由/未完了/次の一手は自分のノートへ保存する。

状態出力にノート・README・手動現況からの値を混ぜない。引継ぎの虚偽・古い記述がコード状態を変更しない。コードだけ変更・ノート未更新でも新しい状態を取得する。原本追跡存在/実体取得/描画成功を区別し、観測していない完成や適用を推測しない。

## 三視点の敵対検証・通電

1. 鮮度・Git整合性: remote更新、dirty checkout、fetch失敗、原本欠落、writer競合、同じSHAの状態/引継ぎ取得。
2. 意味と出典: ノートの古い件数/年度/完成記述が状態へ混入しない。コードと引継ぎの未反映差分が分かる。
3. コード未読スモーク: 実装・テスト・差分を読まず、利用者文書とコマンド出力だけで両入口を操作する。

実GitHub main fetchと、ローカルGitサーバーのmainへコードだけ/ノートだけの後続変更を入れる通電を行う。両入口から同じ新SHAを取得し、それぞれの出力だけが正しく変わることを検証する。本番main反映とは区別する。

旧案の検証は旧設計に対する結果であり、新設計へ流用しない。新設計の結果は再検証後に追記。Chromium修復は保留で、情報取得と描画環境の完了を混同しない。

## 共有開始

実装と結果を作業ブランチへ保存。レビュー・人間の承認・main反映後、両担当の実環境で再取得する。別サービスの既読・自動起動は保証しない。GitHub API403のPR作成制限は残っておりpushはmain反映ではない。
