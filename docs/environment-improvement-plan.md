# 環境構築改善計画と受入条件

ゴールは、CodexとClaude Codeが同じ入口で最新mainの確定情報・正本・両担当の記録を取得し、既存材料を未確認へ戻さず編集を開始できること。ブラウザ導入の復旧は今回の対象外。

## 原因と対策

| 原因 | 対策 |
| --- | --- |
| 古いREADME/AGENTSの状態説明 | 現況を `docs/coordination/current.yaml` へ集約し入口から案内 |
| ノート全文に過去と訂正が混在 | 学校事実はcompany-data、制作判断は共通現況、ノートは根拠・履歴として読む |
| 作業ブランチを最新mainと混同 | Git fetch成功後の固定main SHAから `git show` で読む。checkoutや未保存変更を動かさない |
| 取得失敗後のキャッシュを最新と誤認 | 失敗を非zeroとし、成功時のcontextを再利用させない。offlineは未検証と明示 |
| 片方の変更をもう片方が知らない | 正本の更新と現況の更新を同じPRに入れ、両入口で取得。相手ノートを代理編集しない |

## 構築順序

1. 共通取得コマンド `python3 system/scripts/sync-context.py` を構築。Python標準機能とGitのみ使用しChromium・GitHub APIに依存しない。
2. `docs/coordination/current.yaml` に現況と根拠・適用限界を登録。学校の事実値は複製せず正本を参照。未マージ作業は別欄に隔離。
3. AGENTS/CLAUDE/READMEの開始手順を統一。開始、事実を答える前、編集前、マージ提案前に再取得する。
4. 3視点の独立した敵対検証を実行し、指摘を修正する。
5. 実Git通信の通電と、両エージェント入口からのコード未読スモークを実行。変更を作業ブランチへpushしレビューに供する。

## 受入条件

- 通常実行でfetch成功時のmain SHAとUTC取得時刻、現在checkoutとの違い、未保存変更を表示する。
- 正本・共通現況・両担当ノートを同じ固定SHAから読める。全文を省略せず取得する。
- 作業ブランチ・HEAD・未保存変更を変更しない。未マージ情報をマージ済みの事実に混ぜない。
- fetch失敗・必須ファイル欠落・出力失敗は成功扱いしない。offlineは編集開始の鮮度確認には使えない。
- ターゲット、2028年の冊子、2027年の募集要項、写真79件、認定取得とSNS予定、別ブランチの冊子の状態を正しく区別できる。
- 意味の鮮度はGitだけで保証できないため、正本と現況が矛盾すれば編集を止め、矛盾を具体的に報告する。

## 敵対検証と通電

1. 鮮度・Git整合性: 古いcheckout、未保存変更、fetch失敗、remote更新、必須原本欠落に対する検証。
2. 情報の意味: 古いノートの訂正、原本あり/担当読了/正本登録/採用待ち/不足、適用年度・未マージの境界を検証。
3. ブラックボックス: 実装コードとテストコードを一切読まず、AGENTS/CLAUDEと公開コマンド・出力だけで取得・回答・失敗時の挙動を検証。

実GitHub mainのfetchは現インスタンスの通電として実施。ローカルGitサーバーへの新規マージを両入口から取得する試験も行い、未マージの改修がまだ本番mainに存在しないことと区別する。マージ後は両担当が実mainで再取得し、新しい現況と同じSHAを得たことを確認して共有運用の開始とする。

常に最新とは常時監視を意味せず、必要な判断の直前にfetchして最新スナップショットを読むこと。取得後にmainが進む可能性は残るため、長時間の作業や新しいユーザー訂正の後は再取得する。Gitの取得成功は原本の意味・内容の検証を代替しない。
