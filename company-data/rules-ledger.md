# 運用ルール台帳

Codex・Claude Codeに共通する読み書き・担当・作業手順の正本。現在情報や作業経緯をこの台帳へ重複記載しない。人間の最新の明確な指示を優先する。

## 1. 4台帳と実体の役割

| 台帳 | 記録する内容 | 読む場面 |
| --- | --- | --- |
| [確定台帳](ledger.md) | 最新の最有力情報。項目と記録の2列。記載または空欄のみ | S・開始・再開時に全文 |
| [引継ぎ台帳](handoff-ledger.md) | 担当ごとの再開位置・次の作業・注意点・作業ブランチ | S・開始・再開時に全文（確定台帳と必ず両方） |
| [経緯台帳](history-ledger.md) | 判断・変更の理由と必要な参照先 | 理由を確認する時 |
| この運用ルール台帳 | 読み書き・担当・作業手順 | 開始時と必要時 |

- 確定台帳には最新の最有力情報を記載する。仮説・正式採用などの状態欄、経緯、過去の候補は設けない。情報がない項目は空欄。
- 台帳とフォルダは別。原本・画像・制作コード・設定・検証出力の実体は適切なフォルダへ保存し、台帳から必要な参照先を示す。
- 原本は `references/`、制作物は `books/`、共有素材は `shared/`、学校の写真・ブランド・制作向けデータは `company-data/` に置く。
- 制作向けYAML、分析結果、生成指示、比較レポートは制作に使う実体。現在情報を把握する別台帳として使わない。
- Gitは保存・共有・変更管理に使う。通常の現在情報の把握でGit履歴や経緯を読む必要はない。

## 2. 開始と必須読み込み

- 単独メッセージの `S` は開始、`f` は終了。前後の空白・大文字小文字・半角全角は区別しない。文章・コード・ファイル名の一部では発動しない。
- 「開始して」「最新を読んで再開して」は開始、「終了」「今日は終わり」「引継ぎして」は終了として扱う。
- 開始時は未保存変更と現在のブランチを確認し、変更を破棄・上書きせず最新の共有版を取得する。
- 次のコマンドを実行し、最新mainの確定台帳と引継ぎ台帳を必ず両方全文読む。どちらか一方だけで開始・再開を完了としない。

```bash
python3 system/scripts/read-ledger.py
cat company-data/handoff-ledger.md
```

- `LEDGER_BEGIN` と同じsha256の `LEDGER_END` が見えることを確認する。途中切れなら全文を分割して読む。取得失敗・欠落を読込済みと扱わず、古いキャッシュへ自動で切り替えない。
- 読むのは開始時に1回。会話中の回答・編集ごとには繰り返さない。更新を認識した時、または要約・コンテキスト消失で全文を保持していない時だけ再読する。
- 確定台帳と引継ぎ台帳は開始時に省略せず全文読み、開始報告で読了を明示する。運用ルールはこの台帳を確認し、原本・経緯は今回の作業に必要な時だけ読む。
- 未マージ作業を再開する場合は引継ぎ台帳の担当欄から対象ブランチを選ぶ。未マージ版と共有版を混同しない。
- 未マージ台帳の検証に限り `python3 system/scripts/read-ledger.py --local` を使う。`LOCAL_PREVIEW` を共有版の読込成功と扱わない。
- `sync-context.py` は実体の調査補助であり、通常開始時の必須手順ではない。
- 開始報告では今回の作業、他方との重複、未確認事項を短く伝える。

## 3. 更新とマージ

1. 人間の明確な台帳更新指示を受けて、作業ブランチの確定台帳を書き換える。推測だけで埋めない。
2. 対象項目を最新の最有力情報に置き換え、情報がなくなる項目は空欄にする。過去の内容を同じ欄へ積み上げない。
3. 原本・実体と参照先を確認し、制作データも変更する指示の場合は関連する実体を整合させる。
4. 変更を検証し、commit・pushする。作業ブランチへの保存とmain反映を区別して報告する。
5. 人間の明示的なマージ指示でmainへ反映する。この時点で全員が読む確定台帳の共有版が更新される。
6. 更新を認識した担当は確定台帳全文を再読する。

- 書き込みは更新指示を受けた時、共有版への反映はマージ時。更新指示や `f` はマージ承認を兼ねない。
- 引継ぎは再開に必要な内容を引継ぎ台帳へ、判断・変更理由は経緯台帳へ記録する。確定情報を他台帳へ複写しない。
- 自社の過去年度の原本について、年度更新で変わる表記（日程の年、「○年○月○日時点で満○歳以上」等）と、2学科化前の版の学科・定員の相違は、不備として報告・警告しない。確定台帳の2学科（国際ビジネスAI科・総合ビジネス科）が正しい。
- 学校の事実を外部の参考資料から転用しない。学校の原本や人間の指示を確認する。原本の適用年度と今回の対象年度を混同しない。

## 4. 担当と並行作業

| 担当 | 主な領域 |
| --- | --- |
| Codex | 紙面制作、画像生成・編集、BOOKのHTML/CSS/SVG配置、視覚レビュー |
| Claude Code | 共通エンジン・CLI・検証、環境構築、データ構造・自社情報、運用ドキュメント |

- Claude Codeは制作範囲（紙面制作、画像生成・編集、BOOKのHTML/CSS/SVG配置、視覚レビュー、`books/` の制作物、`shared/generated-assets/` の生成素材）に触れない。人間が制作を明示指示した場合も、実施前に担当外であることを伝えて確認する。
- 両者は同じ台帳・データ・制作形式・検証基準を使う。通常は別ワークスペース・別ブランチで作業する。
- 着手前に引継ぎ台帳と必要な作業ブランチを確認し、変更するファイルの重複を調べる。他方の状態を確認できない場合は「作業していない」と断定しない。
- 担当外の変更が必要なら、対象・通常の担当・衝突の可能性を説明して人間の選択を待つ。今回の範囲について明示承認済みなら再確認しない。
- 同じ箇所の並行変更を発見したら変更を止め、分担を確認する。他方の作業内容を無断で変更しない。
- 人間が指定した台帳への集約・棚卸し・運用整備は、この依頼の範囲でCodexが進める。
- サブエージェントを使う場合は変更対象を分け、統合担当が全体の整合を確認する。

## 5. 作業・検証・終了

- 原則は作業ブランチとPRで共有する。履歴の強制書換えや他方のブランチの無断変更をしない。
- commitメッセージは日本語・種別付き（`feat` / `fix` / `book` / `data` / `ref` / `docs` / `chore`）。1コミットは意味のある作業単位にする。
- 制作変更は `npm run doctor`、`npm run check`、変更したBOOKのrender、出力画像の目視で検証する。未実行・失敗・未確認を合格にしない。GitHub ActionsのCIは使わない。
- Chromium取得は通信制限のため保留する。人間の新たな指示なしに取得を繰り返さない。Chromium依存の未実行検証は明記する。
- 終了時は安全な区切りで止め、変更・検証結果・未完了を確認し、引継ぎ台帳の自分の担当欄を更新する。次の作業、注意点、ブランチと必要な参照先を残す。
- commit・pushし、最新mainとの衝突・影響を確認してマージを提案する。承認待ちや検証不合格の途中保存は未マージのまま終了できる。
- 保存できなければローカル変更を保全し、失敗理由と再開方法を報告する。push成功を相手の確認やmain反映と同一視しない。
- 最終報告には保存結果、ブランチ/PR、残りと次の作業を記載する。
- バイナリは `.gitattributes` のGit LFS規則に従う。認証情報、`node_modules`、キャッシュ、作業用一時ファイル、シンボリックリンクはコミットしない。
- `docs/concept.md` は構想原本として編集しない。保護機構の導入はbaseline確定後の指示に従う。

## 7. 制作ハーネス

紙面・冊子制作や品質改善では `.agents/skills/dtp-production/SKILL.md` を適用する。編集制作、独立レビュアー、編集長の3役を別エージェントで実行し、修正と再レビューを行う。パーツデザイナーは冊子ライン外の部品供給役として `.agents/skills/dtp-parts/SKILL.md` を使う。依頼内容・全見開き・可読性・出力を確認し、同じ最終PDFへの独立レビューと編集長判断がそろった場合にのみ提出する。人間は最終採用を判断し、制作ミスの検出係にはしない。

登録は公式形式の `.codex/config.toml` と役割TOML。対応ホストではプロジェクト設定の読み込みを確認する。カスタム役割を選べないホストでは役割指示を別エージェントへ渡すが、登録設定やsandboxが適用されたとは報告しない。成果物の検査記録はBOOKのreviewsフォルダ、現在情報・引継ぎ・経緯・ルールは4台帳の役割を守る。

冊子の目的・読者は確定台帳の該当項目を共通の既定値とし、制作依頼のたびに再指定を求めない。編集長がその目的・読者と人間のデザイン方針を制作ブリーフへまとめ、各役へ渡す。変更は人間の明確な更新指示による。

共通デザイン方針と避ける表現は確定台帳を参照する。全制作役が同じ方針を既定値として使う。読者の理解を、見た目の派手さや文章量の少なさだけで合格判定しない。対象者による確認は実施の有無を区別する。

制作の役別優先順位・原本比較・具体的な差し戻し条件は `.agents/skills/dtp-production/design-contract.md` に従う。役割名だけで起動せず役割指示全文を渡す。代表見開きの方向審査を経て全体へ展開し、技術合格でデザイン未達を許容しない。

## 8. 役割プロンプトの調査・採用・差し替え

- 調査原文は `references/research/public-prompts-20261012/`、全件評価は `references/research/prompt-evaluation-20261012/` に保存する。原文・取得元・ライセンス・SHAを残し、要約や採用版で原文を上書きしない。未採用・不適合の候補も人間の削除指示なしに捨てない。
- 有望な方法から `system/prompts/agent-role-template.md` の型へ当てはめる。役割固有の責任、専門的方法、合格・差し戻し条件を具体化し、出典と冊子向け変更を記載する。原文をそのまま使う場合と編集する場合を区別する。
- 候補は `system/prompts/role-candidates/` に版別に残す。変更前の設定も保存する。`selection.json` は実行候補を指定する設定であり、新たな情報台帳ではない。
- 実行設定と選択設定を揃えて変更し、Claude用を共通TOMLから生成・同期確認する。候補の過去版を残すことで、一役ずつ差し替え・復帰できる。
- 実紙面で検証し、機能しなければ修正または別候補へ交換する。構文・同期成功だけで品質を検証済みにしない。変更理由は経緯台帳、再開位置は引継ぎ台帳、紙面での検証証拠はBOOKのreviewsに記載する。
- 詳細な保存場所・初回の選出根拠・差し替え手順は [候補運用](../system/prompts/role-candidates/README.md) を参照する。マージは人間の明示指示による。

- 人間の最新指示により、余白拡大・短文化・分かりやすさへの一律の優先を解除した。役割候補v2と更新済み判断契約を使い、停止されたv1へ自動復帰しない。

- 港の水彩生成画像 `seaside-watercolor-example.png`（SHA256 `5f4524e5484a1c5aa3af6cd3cd39e462818e9dbeb03e5c8bf0992de927f3db6e`）は人間の明示指示で制作ストックから削除。旧紙面の検証履歴に含まれていても、素材や切り出し元として再利用しない。
